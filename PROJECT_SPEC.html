1. Project overview

Order Notebook is a multi-tenant SaaS platform for Myanmar SMBs that sell through messenger and social channels. Staff record orders on behalf of customers, track inventory, manage CRM, monitor sales, and fulfill advance/pre-orders with deposit and balance collection.

The product is staff-only in v1 — no customer portal or storefront. The web console is the active priority; mobile implementation is deferred to a later phase while the shared versioned API remains reusable.

The AI order-drafting assistant turns messenger-style text into structured drafts (customer, line items, qty, notes) for human review. Each shop uses its own LLM API key (BYOK).

1.1 Problem statement

Myanmar shops track orders in notebooks, spreadsheets, and chat threads. Deposits, partial payments, reservations, and fulfillment dates get lost. Order Notebook centralizes this in a bilingual system aligned with messenger-led sales.

2. Goals and success measures

2.1 Goals

  1. Register and record first messenger order in under 15 minutes.
  2. Reduce lost pre-orders via deposit → reserve → fulfill → balance workflow.
  3. Accurate simple-catalog stock without ERP complexity.
  4. Single customer view: contact, notes, order history.
  5. Actionable sales and pre-order pipeline reports.
  6. Faster entry via AI drafts (always human-confirmed).
  7. Core workflows on a mobile-first responsive web console; mobile parity later.

2.2 Success measures

  • Shop activation rate (signup → product → order) within 7 days
  • Median order creation time (with/without AI)
  • Pre-order SLA adherence
  • Deposit/balance reconciliation errors
  • AI draft acceptance rate
  • Weekly active shops; API p95 latency; tenant isolation security

6. Non-functional requirements

Security

  • Tenant isolation on every query
  • bcrypt/argon2 passwords; JWT rotation
  • Encrypted BYOK keys; rate limits
  • Audit: status, payments, stock, AI confirms

Performance & reliability

  • API p95 < 300ms (indexed)
  • AI timeout 30s
  • Daily PG backups; idempotent payments
  • Optimistic locking on stock

A11y: WCAG 2.1 AA (web); touch targets + screen reader labels (mobile).

Standard-order fulfillment lifecycle

TO_DELIVER→ DELIVERED

Saving a standard order deducts stock immediately. COD stays unpaid until collection is recorded. On delivery, staff choose where the rider paid them and can record a collection fee; gross receipt and fee are posted together so cashbook balances show net proceeds. Cancelling before delivery restores stock.

Pre-order fulfillment lifecycle

1. Create pre-order — customer, items, expected date, required deposit
2. Record deposit → DEPOSIT_PAID → stock reserved
3. Pipeline view by status (web kanban / mobile segments)
4. Mark READY_TO_FULFILL when stock arrives
5. Fulfill → FULFILLED → collect balance
6. Final payment → COMPLETED

AI assistant flow

  1. Paste messenger text or describe order
  2. Backend returns editable OrderDraft
  3. Staff edits customer/items/qty
  4. Confirm persists the order into its operational initial status
