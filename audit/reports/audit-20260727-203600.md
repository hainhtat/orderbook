# Audit Report

- **Scope:** Milestone 1 products, categories, customers, and related authentication/tenant boundaries across backend, web, and mobile
- **Timestamp:** 2026-07-27 20:36:00 UTC+06:30
- **Method:** Static review of `PROJECT_SPEC.md`, implementation, schemas, client data flows, and existing tests

## Overall risk summary

Milestone 1 is **not production-ready**. Route-level authentication and membership resolution are consistently applied, entity lookups generally include `shopId`, mobile tokens use SecureStore, and client query caches are cleared on logout. However, a cross-tenant category-reference flaw, non-atomic inventory updates, the absence of a production PostgreSQL schema/migration path, and missing authentication throttling create material security, integrity, availability, and deployment risks.

Findings: **0 Critical, 4 High, 6 Medium, 3 Low**.

## Critical

No critical findings.

## High

### H1 — Products can reference another tenant's category

- **Affected:** `backend/src/api/v1/products/product.validators.ts`, `backend/src/api/v1/products/product.service.ts`, `backend/prisma/sqlite/schema.prisma`
- **Why it matters:** Product create/update accepts any syntactically non-empty `categoryId` and writes it directly. The service never verifies that the category belongs to the authenticated `shopId`; the foreign key is only on category `id`.
- **Likely impact:** An authenticated shop owner who obtains or guesses another category ID can create a cross-tenant association. This violates strict tenant isolation and can become direct data disclosure when category relations are included in later responses, exports, or order-assistant context.
- **Mitigation:** Resolve categories with `{ id: categoryId, shopId }` before writes and reject mismatches as 404/422. Prefer a schema design that enforces tenant-consistent relations (for PostgreSQL, a composite `(shopId, id)` candidate key referenced by `(shopId, categoryId)`). Add negative integration tests using two shops for create and update.

### H2 — Concurrent stock adjustments lose inventory updates while preserving misleading audit rows

- **Affected:** `backend/src/api/v1/products/product.service.ts` (`adjustStock`)
- **Why it matters:** Current stock is read before the transaction; the transaction then writes an absolute `nextQty`. Two simultaneous adjustments can read the same value, both insert an audit row, and overwrite each other so only one delta is represented in `stockQty`.
- **Likely impact:** Inventory drift, false availability, incorrect low-stock state, and an audit trail whose deltas do not reconcile with the product balance. The negative-stock check is also subject to the same race.
- **Mitigation:** Perform a guarded atomic increment inside one transaction, scoped by `shopId`, with a version/optimistic-lock predicate or serializable retry. Enforce the non-negative invariant in the atomic update and only create the adjustment row after the guarded update succeeds. Add concurrent adjustment tests.

### H3 — Production PostgreSQL deployment path is absent

- **Affected:** `backend/prisma/`, `backend/src/database/client.ts`, `backend/package.json`
- **Why it matters:** The repository contains only `prisma/sqlite/schema.prisma`; the application imports the generated SQLite client, and all database scripts target SQLite. There are no PostgreSQL schema files or migrations despite the specification declaring PostgreSQL canonical for production.
- **Likely impact:** The backend cannot safely deploy against the intended production datastore. SQLite also lacks the expected concurrency/scaling behavior, operational backup/PITR path, and production indexes.
- **Mitigation:** Add a canonical PostgreSQL Prisma schema and checked-in migrations, generate/import the production client, provide explicit dev/test versus production commands, and run migration validation plus integration tests against PostgreSQL in CI. Do not promote the SQLite schema directly to production.

### H4 — Authentication endpoints have no rate limiting

- **Affected:** `backend/src/app.ts`, `backend/src/api/v1/auth/auth.routes.ts`, `backend/package.json`
- **Why it matters:** Register, login, and refresh are publicly reachable without per-IP/account throttling. This directly conflicts with the security requirement to rate-limit auth endpoints.
- **Likely impact:** Password brute force, credential stuffing, user enumeration pressure through response timing, registration abuse, and bcrypt-driven application denial of service.
- **Mitigation:** Add proxy-aware, distributed rate limits for login/register/refresh, keyed by normalized account and client IP with conservative burst limits. Return stable 429 errors, instrument rejected attempts, and consider progressive backoff/account protection.

## Medium

### M1 — Lists and customer order history are unbounded

- **Affected:** `backend/src/api/v1/products/product.service.ts`, `backend/src/api/v1/customers/customer.service.ts`, corresponding web/mobile list screens
- **Why it matters:** Products, customers, and per-customer orders use unbounded `findMany` calls. Web renders complete tables; mobile downloads all products and performs product search locally. Customer `contains` search performs scan-prone OR matching, and product search/category/low-stock filtering required by the spec is absent server-side.
- **Likely impact:** Increasing latency, database/Node memory pressure, oversized PII responses, slow web rendering, and excessive mobile bandwidth. This is incompatible with the 10k-product latency target and will worsen with tenant size.
- **Mitigation:** Add cursor pagination with enforced maximum page sizes and stable ordering; move search/filtering server-side; return minimal list projections. Add PostgreSQL indexes supporting tenant plus sort/filter fields and use appropriate text-search/trigram strategy after measuring query plans.

### M2 — M1 input validation is too permissive and can turn client mistakes into 500s

- **Affected:** product/customer validators and services; `backend/src/middleware/error-handler.ts`
- **Why it matters:** Names, SKUs, phones, notes, reasons, IDs, and search strings lack practical maximum lengths. Numeric inputs are not bounded to Prisma/DB-safe ranges, `deltaQty` permits zero, stock reasons are arbitrary, update `imageUrl` accepts any string, and foreign-key failures such as an unknown category are not mapped from Prisma `P2003`.
- **Likely impact:** Oversized records and expensive searches, inconsistent audit data, integer/ORM failures, unsafe external image schemes or tracking URLs, and generic 500 responses for invalid client input.
- **Mitigation:** Define shared domain limits, safe integer ranges, normalized/validated phone rules, an allowed stock-reason enum, and HTTP(S)-only image URLs. Reject zero adjustments. Validate referenced entities explicitly and map expected constraint failures to stable 4xx errors.

### M3 — Duplicate-phone behavior is both bypassable and stricter than the contract

- **Affected:** `backend/src/api/v1/customers/customer.service.ts`, `backend/prisma/sqlite/schema.prisma`, customer forms
- **Why it matters:** Duplicate detection compares only trimmed raw text, so equivalent Myanmar numbers in different formats can bypass it. Conversely, a unique constraint and 409 response make duplicates impossible, while CRM-02 specifies a warning/hint rather than a mandatory rejection.
- **Likely impact:** Duplicate customer records despite the feature, or blocked legitimate shared-phone workflows; clients cannot confirm an intentional duplicate.
- **Mitigation:** Define and persist a normalized phone key, return duplicate candidates as a warning, and support an explicit confirmation/override if duplicates are allowed. If uniqueness is intentionally mandatory, update the specification through `@spec-maintainer`.

### M4 — Web refresh tokens are available to any successful XSS

- **Affected:** `frontend/src/features/auth/token-storage.ts`, `frontend/src/lib/api-client.ts`
- **Why it matters:** Both access and long-lived refresh tokens are persisted in `localStorage`. Any script execution in the application origin can exfiltrate the refresh token and retain account access beyond the access-token lifetime.
- **Likely impact:** Full shop-session takeover, including customer PII and inventory mutation.
- **Mitigation:** Prefer an HttpOnly, Secure, SameSite refresh cookie with access tokens held only in memory; add CSRF protection where required. Independently deploy a strict CSP and security headers, minimize third-party script exposure, and rotate/revoke refresh sessions on suspected compromise.

### M5 — Milestone 1 exit criteria are not implemented across clients

- **Affected:** mobile product/customer features, backend category routes, web/mobile category and image workflows
- **Why it matters:** Mobile products are read-only; there is no product create/update/archive, stock adjustment, or category management. Mobile customers can be created but not updated/deleted. Backend categories expose only list/create despite category CRUD, and image upload is absent (only a URL field exists).
- **Likely impact:** The specified “owner manages catalog and customers on web and mobile” workflow cannot be completed, creating operational inconsistency and forcing users to switch platforms.
- **Mitigation:** Complete the missing mutations and guarded UI states, or explicitly redefine/defer the milestone scope. If the omissions are intentional product decisions, synchronize the spec via `@spec-maintainer`.

### M6 — No backend regression coverage exists for M1 authorization or mutations

- **Affected:** `backend/tests/`
- **Why it matters:** Existing backend tests cover auth and slugification only. There are no product, category, customer, stock-concurrency, cross-tenant, validation, pagination, or suspended-shop tests. Mobile has no M1 behavior tests.
- **Likely impact:** Tenant regressions and inventory-integrity defects can ship undetected; passing current tests provides no assurance for the Milestone 1 exit criterion that tenant isolation is verified.
- **Mitigation:** Add focused two-tenant integration tests for every M1 read/write route, cross-tenant IDs and category references, suspended shops, duplicate phones, limits, archive behavior, and concurrent stock changes. Add a small set of mobile mutation/error-state tests as those flows are implemented.

## Low

### L1 — JWT secret policy is weak for HS256

- **Affected:** `backend/src/config/env.ts`, `backend/src/utilities/tokens.ts`
- **Why it matters:** Production accepts a 16-character `JWT_SECRET` for HS256.
- **Likely impact:** Weak operator-supplied secrets reduce resistance to offline guessing if tokens or configuration metadata are exposed.
- **Mitigation:** Require at least 32 random bytes (preferably validated as base64/hex with entropy guidance), support key rotation, and keep secrets in a managed secret store.

### L2 — Refresh-session expiry ignores configured token TTL

- **Affected:** `backend/src/api/v1/auth/auth.service.ts`, `backend/src/config/env.ts`
- **Why it matters:** JWT refresh expiry uses `REFRESH_TOKEN_TTL`, but the database session always expires in seven days. Expired rows also have no visible cleanup path.
- **Likely impact:** Configuration changes produce surprising early rejection or stale session rows, complicating incident response and operations.
- **Mitigation:** Parse one validated refresh duration for both JWT and database expiry, and periodically purge expired sessions.

### L3 — Baseline HTTP hardening is absent

- **Affected:** `backend/src/app.ts`, backend dependencies/deployment configuration
- **Why it matters:** No application-level security-header middleware is configured; production HTTPS enforcement/HSTS is not evidenced in the repository.
- **Likely impact:** Weaker browser defenses against content sniffing, clickjacking, and downgrade/misconfiguration scenarios.
- **Mitigation:** Apply vetted security headers (including HSTS at the HTTPS edge and a CSP appropriate for the web app), document TLS termination, and add production configuration checks.

## Residual risks / follow-up checks

- This was a static audit; no production-like PostgreSQL environment exists to validate migrations, query plans, concurrency, backup recovery, or p95 latency.
- Re-audit tenant isolation after relation enforcement and run adversarial two-shop API tests, including arbitrary `X-Shop-Id`, foreign resource IDs, suspended shops, and concurrent requests.
- Load-test paginated catalog/customer endpoints with at least 10k products and realistic customer/order volumes.
- Verify deployed CSP/TLS/HSTS, rate-limit storage, log redaction, mobile SecureStore platform settings, and refresh-session revocation behavior.
- **Spec sync:** Needed only if duplicate phones are intentionally hard-unique, category/image CRUD is deliberately reduced, or mobile mutation workflows are intentionally deferred. Otherwise these are implementation gaps against the current specification.
