## Overall risk summary

The implementation has strong tenant scoping on the inspected order/product/customer routes and correctly uses transactions for most inventory/payment mutations. Unit tests pass, but the full backend integration suite currently fails on a Milestone 3 contract assertion. There is also a significant scalability risk from unbounded list endpoints and a reliability risk in the pre-order stock lifecycle.

## Critical

None found.

## High

### H-01 — Payment API returns stale pre-order status after reservation

**Affected area:** `backend/src/api/v1/orders/order.service.ts` (`recordPayment`, approximately lines 620–655); `tests/integration/preorders-milestone-3.test.ts`.

**Why it matters:** When the minimum deposit is recorded, the transaction updates the order from `CONFIRMED` to `RESERVED` (or `AWAITING_STOCK`) after creating `updated`. The returned payload is built from the earlier `updated` object, so the API response still reports `CONFIRMED` even though the database row is already in the next state.

**Impact:** Frontend clients can render the wrong pipeline state, fail to show reservation badges, and make an incorrect follow-up action. The full integration suite currently fails (`expected RESERVED`, received `CONFIRMED`).

**Recommended mitigation:** After the status update, return the final order including payments (or re-read the order inside the transaction) and serialize that final object. Add assertions for both `RESERVED` and `AWAITING_STOCK` response contracts.

### H-02 — AWAITING_STOCK orders have no replenishment/reconciliation path

**Affected area:** `backend/src/api/v1/orders/order.service.ts` pre-order transitions and payment logic; product stock-adjustment flow.

**Why it matters:** The specification requires `AWAITING_STOCK → RESERVED` when stock is replenished. Current code can set `AWAITING_STOCK`, but no stock-adjustment or reconciliation path automatically (or transactionally) retries reservations when inventory later increases. The transition map exposes `AWAITING_STOCK → RESERVED`, but the caller must provide a status transition without a stock-aware reservation operation.

**Impact:** Pre-orders can remain indefinitely stuck, inventory may be reserved incorrectly if staff manually transitions at the wrong time, and the deposit → reserve → fulfill workflow is not reliable under normal restocking.

**Recommended mitigation:** Centralize reservation eligibility and invoke it after stock adjustments (or provide a dedicated “reserve when available” service). Re-check all line items atomically, update `reservedQty`/stock, create adjustment/history records, and add integration coverage for restock followed by reservation.

## Medium

### M-01 — Order and customer list endpoints are unbounded

**Affected area:** `backend/src/api/v1/orders/order.service.ts:list`; `backend/src/api/v1/customers/customer.service.ts:list`; frontend list consumers.

**Why it matters:** Both endpoints call `findMany` without pagination/limit. Orders include all line items and all payments; customers compute last-order data per record. The product endpoint also loads the complete product list and performs a grouped sales query.

**Impact:** Response size, database work, and browser rendering grow linearly with tenant history. A large shop can experience high latency, memory pressure, and expensive repeated requests from mobile-width web screens.

**Recommended mitigation:** Add cursor or offset pagination with bounded defaults, return `total/nextCursor` metadata, and paginate customer order history. Add/verify indexes for `(shopId, createdAt)`, `(shopId, status, createdAt)`, and searchable customer/order fields as supported by the production database.

### M-02 — Inventory quantities have ambiguous `stockQty`/`reservedQty` semantics

**Affected area:** `backend/src/api/v1/orders/order.service.ts`; `backend/src/api/v1/products/product.service.ts`; Prisma `Product` model.

**Why it matters:** Reservation decrements `stockQty` and increments `reservedQty`, while `availableStock` is serialized directly from `stockQty` rather than explicitly calculating “on-hand minus reservations” as required by CAT-06. This can be internally consistent only if `stockQty` means sellable-unreserved stock, but the schema/spec describe stock quantity as on-hand and separately track reservations.

**Impact:** Stock adjustment screens, low-stock calculations, reports, and future reconciliation can disagree about actual on-hand inventory. Negative or mismatched reserved quantities are possible if releases and manual adjustments are not coordinated.

**Recommended mitigation:** Define one invariant (for example `onHandQty`, `reservedQty`, `availableStock = onHandQty - reservedQty`) and enforce it in one domain service. Add invariant tests across sale, reservation, release, cancellation, and manual adjustment.

### M-03 — Product sales summaries are computed from full product lists

**Affected area:** `backend/src/api/v1/products/product.service.ts:list`.

**Why it matters:** The service first loads all matching products, then groups sales for every returned product. There is no page bound and no date scope.

**Impact:** Catalog screens become increasingly expensive as orders/products grow; repeated mobile refreshes amplify database load.

**Recommended mitigation:** Paginate products and aggregate only the page IDs (or expose summaries through a dedicated report query/materialized aggregate for larger tenants).

## Low

### L-01 — Broad status validators retain legacy states

**Affected area:** `backend/src/api/v1/orders/order.validators.ts`.

**Why it matters:** Validators accept `TO_CONFIRM` and legacy pre-order states alongside the current standard flow. The service correctly rejects invalid transitions, but stale statuses remain part of the public input contract.

**Impact:** API consumers can submit states that are not user-visible in the current web flow, increasing contract ambiguity.

**Recommended mitigation:** Keep legacy values only while migration compatibility is required; otherwise narrow validators to the documented state machine and maintain an explicit migration/versioning note.
