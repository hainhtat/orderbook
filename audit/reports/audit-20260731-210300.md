# Audit Report

**Audited scope:** Full project review (M0–M3 web-first baseline, shared API, deferred mobile client) against `PROJECT_SPEC.md` v1.6
**Timestamp:** 2026-07-31 21:03 (Asia/Yangon)
**Method:** Static review of backend/frontend/mobile, schema, tests, and verification command output

## Overall risk summary

The codebase is **suitable for continued milestone work on the web console**, with strong tenant scoping on inspected routes, transactional order/stock mutations, and passing integration tests for M1–M3 happy paths. It is **not production-ready**: no PostgreSQL deployment path, no auth rate limiting, refresh tokens in web `localStorage`, and several scalability/contract issues on list filtering and customer aggregates.

Findings: **0 Critical, 3 High, 7 Medium, 4 Low**.

## Critical

No critical findings.

## High

### H-01 — Web refresh tokens persisted in `localStorage`

- **Affected:** `frontend/src/features/auth/token-storage.ts`, `frontend/src/lib/api-client.ts`
- **Why it matters:** Long-lived refresh tokens are readable by any script running in the app origin. A successful XSS yields persistent session takeover beyond access-token lifetime.
- **Likely impact:** Full shop access, PII exfiltration, fraudulent orders/payments.
- **Mitigation:** Move refresh to HttpOnly Secure SameSite cookies; keep access tokens in memory where feasible. Add CSP and minimize third-party scripts. Document rotation/revocation procedures.

### H-02 — `paymentStatus` list filter is applied after DB pagination

- **Affected:** `backend/src/api/v1/orders/order.service.ts` (`list`, lines ~206–210)
- **Why it matters:** `paymentStatus` is derived in application code, not stored. The service paginates in SQL, then filters the current page in memory. Pages can be empty or incomplete while `pagination.total` reflects unfiltered counts.
- **Likely impact:** Incorrect order list UX, missed COD/unpaid orders, unreliable staff workflows when filtering by payment state.
- **Mitigation:** Push payment-status predicates into SQL (`amountPaidMMK` vs `totalMMK`) or compute in a subquery/view. Add integration tests for paginated `paymentStatus` filters across multiple pages.

### H-03 — No production PostgreSQL path

- **Affected:** `backend/prisma/` (SQLite schema + migrations only), `backend/src/database/client.ts`
- **Why it matters:** Spec declares PostgreSQL canonical for production. Only SQLite is configured; generated client targets SQLite.
- **Likely impact:** Cannot deploy to intended production datastore; SQLite concurrency/backup limitations under multi-user load.
- **Mitigation:** Add PostgreSQL schema/migrations, environment-specific client generation, CI validation against PostgreSQL, and operational backup/PITR runbooks before pilot.

## Medium

### M-01 — Customer detail missing CRM-03 aggregates and pagination

- **Affected:** `backend/src/api/v1/customers/customer.service.ts` (`orderHistory`), `frontend/src/features/customers/customer-detail-page.tsx`
- **Why it matters:** Spec requires paginated order history, lifetime spend, and open pre-order count. Current `orderHistory` is an unbounded `findMany`; UI renders all rows with no spend/pre-order summary.
- **Likely impact:** Slow customer detail for active shops; staff lack required CRM context.
- **Mitigation:** Add paginated `/customers/:id/orders` with aggregates endpoint or enriched detail DTO. Wire web UI to match spec.

### M-02 — Authentication endpoints have no rate limiting

- **Affected:** `backend/src/app.ts`, `backend/src/api/v1/auth/auth.routes.ts`
- **Why it matters:** Register/login/refresh are public without throttling (M6 requirement, security baseline).
- **Likely impact:** Brute force, credential stuffing, bcrypt DoS via registration spam.
- **Mitigation:** Add proxy-aware rate limits (IP + normalized email), stable 429 responses, metrics on rejected attempts.

### M-03 — Duplicate phone is hard-rejected, not warned (CRM-02)

- **Affected:** `backend/src/api/v1/customers/customer.service.ts`, customer forms
- **Why it matters:** Spec describes a duplicate-phone **warning** on create; implementation uses unique constraint + 409 conflict.
- **Likely impact:** Legitimate shared-phone workflows blocked unless spec is intentionally strict.
- **Mitigation:** Either implement warning/confirm flow or sync spec via `@spec-maintainer` if hard uniqueness is intentional.

### M-04 — Category update/delete API without web management UI

- **Affected:** `backend/src/api/v1/products/product.routes.ts`, `frontend/src/features/products/api.ts`
- **Why it matters:** M1 expects category CRUD; backend supports list/create/patch/delete but web only creates inline during product form.
- **Likely impact:** Staff cannot rename/remove categories without API tools; orphaned categories accumulate.
- **Mitigation:** Add minimal category management UI or document URL-only/image deferrals in spec.

### M-05 — Pre-order replenishment audit rows use `deltaQty: 0`

- **Affected:** `backend/src/api/v1/products/product.service.ts` (AWAITING_STOCK → RESERVED on positive stock adjust)
- **Why it matters:** Reservation increments `reservedQty` but writes stock adjustment with zero delta, weakening inventory audit reconciliation.
- **Likely impact:** Audit trail does not explain reserved quantity changes; harder to debug stock discrepancies.
- **Mitigation:** Record meaningful adjustment notes/deltas or a dedicated reservation ledger; test AWAITING_STOCK replenishment path.

### M-06 — Mobile client contract drift (deferred but present in repo)

- **Affected:** `mobile/src/features/orders/order-types.ts`, `OrderDetailScreen.tsx`
- **Why it matters:** Mobile models statuses `DRAFT|CONFIRMED|COMPLETED` while API uses `TO_DELIVER|DELIVERED|…`. Transition buttons will fail for standard orders created via API. Spec v1.6 defers mobile, but the code misleads future parity work.
- **Likely impact:** Broken mobile order workflow if used before realignment; wasted QA effort.
- **Mitigation:** Freeze mobile order work until web milestones stabilize; add a prominent deferral note in mobile README or gate routes. Realign types/FSM when mobile phase resumes.

### M-07 — Unbounded or weakly bounded list endpoints remain

- **Affected:** `customer.service.orderHistory`, category list, product list without enforced max `limit`
- **Why it matters:** Orders/customers now paginate, but several auxiliary lists do not. Spec targets 10k-product shops.
- **Likely impact:** Memory/latency growth as tenants scale.
- **Mitigation:** Enforce max page sizes everywhere; add indexes per spec §7.3; load-test list endpoints.

## Low

### L-01 — JWT secret minimum length is 16 characters for HS256

- **Affected:** `backend/src/config/env.ts`
- **Why it matters:** Weak operator-chosen secrets reduce offline guessing resistance.
- **Mitigation:** Require ≥32 bytes entropy; document generation; prefer managed secrets in production.

### L-02 — Product images are URL-only (no upload)

- **Affected:** product forms across web/mobile
- **Why it matters:** M1 mentions optional image URL/upload; upload path deferred.
- **Mitigation:** Track as known gap; confirm object-storage approach before pilot.

### L-03 — Backend unit test surface is thin

- **Affected:** `backend/tests/unit/` (2 tests)
- **Why it matters:** Most behavior relies on integration tests; regressions in pure logic may slip through if integration coverage misses an edge.
- **Mitigation:** Add focused unit tests for FSM maps, payment-status derivation, and clipboard formatting (already partially covered).

### L-04 — No application-level security headers middleware

- **Affected:** `backend/src/app.ts`
- **Why it matters:** Missing baseline HSTS/CSP/frame protections at app layer (may be handled at edge, not evidenced in repo).
- **Mitigation:** Apply vetted helmet/security headers at reverse proxy or Express; document TLS termination.

## Residual risks / follow-up checks

- Re-run adversarial two-tenant tests for orders, payments, and cross-shop IDs before pilot.
- Load-test paginated order/customer endpoints with realistic volumes.
- Verify AWAITING_STOCK → RESERVED replenishment under concurrent stock adjustments.
- Confirm deployed CSP/TLS and refresh-token storage before any external pilot.
- **Spec sync:** Consider `@spec-maintainer` if CRM-02 hard uniqueness, DEPOSIT_PAID as history-only (not persisted status), or mobile deferral should be reflected more explicitly in API docs.
