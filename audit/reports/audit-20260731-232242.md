# Audit Report

**Audited scope:** Full web-first Order Notebook implementation through Milestone 4 (M0–M4), including authentication/tenancy, catalog and CRM, orders/payments, inventory and pre-orders, reports/dashboard/CSV, and cross-cutting production readiness
**Timestamp:** 2026-07-31 23:22:42 Asia/Yangon
**Source of truth:** `PROJECT_SPEC.md` v1.6
**Method:** Static review of backend, Prisma schema, frontend, and tests; regression review of audits `20260731-210300` and `20260731-214700`; unit/typecheck/build/frontend test checks. A concurrent audit integration run was invalidated by the suite's shared fixed SQLite test database, while the independent verifier's isolated run passed all 20 integration tests.

## Overall risk summary

Milestone 4's functional hardening is materially improved: all report routes are authenticated and tenant-scoped; date ranges are capped at 366 Myanmar calendar days; CSV is streamed in 500-row batches and excludes cancelled orders; the active pre-order pipeline excludes terminal states; CSV downloads use coordinated access-token refresh; and report/dashboard frontend tests now exist. M4 is suitable for functional acceptance after the independent verifier passes it.

The repository is **not production/pilot ready**. The largest risks are race conditions in payment, stock reservation, and order numbering; persistent browser refresh tokens; spreadsheet-formula injection in CSV exports; and the absence of the specified PostgreSQL production path. Report aggregation and several paginated lists also still load tenant-wide result sets into application memory.

**Findings:** 0 Critical, 5 High, 6 Medium, 4 Low.

## Critical

No critical findings were identified. Inspected shop-resource and report routes consistently apply authentication plus tenant membership middleware, and inspected queries scope reads by `shopId`.

## High

### H-01 — Concurrent payments and pre-order reservations can corrupt financial and inventory state

- **Affected:** `backend/src/api/v1/orders/order.service.ts` (`recordPayment`, deposit reservation path); `backend/src/api/v1/products/product.service.ts` (awaiting-stock reconciliation)
- **Why it matters:** Payment validation reads the current balance and then increments it without an atomic compare-and-update predicate. Two concurrent requests can both pass the stale balance check and overpay the order. Deposit reservation reads `stockQty - reservedQty`, then increments `reservedQty` separately; simultaneous deposits/replenishment reconciliation can over-reserve the same stock.
- **Likely impact:** `amountPaidMMK > totalMMK`, negative effective availability, duplicate reservation allocation, and reports that no longer reconcile with payments/inventory.
- **Recommended mitigation:** Use atomic conditional updates or row locking in PostgreSQL, with a transaction-isolation strategy and retry on serialization conflicts. Make payment requests idempotent. Add parallel-request integration tests for final balance collection, two deposits competing for the same stock, and replenishment reconciliation.

### H-02 — Web refresh tokens remain readable from `localStorage`

- **Affected:** `frontend/src/features/auth/token-storage.ts`, `frontend/src/lib/api-client.ts`
- **Why it matters:** Any successful same-origin XSS can exfiltrate the seven-day refresh token and sustain shop-owner access after the access token expires.
- **Likely impact:** Persistent session takeover, customer PII exposure, fraudulent order/payment/inventory changes, and report export.
- **Recommended mitigation:** Move refresh tokens to `HttpOnly`, `Secure`, `SameSite` cookies and keep access tokens in memory where feasible. Add a restrictive CSP and document session revocation. Preserve refresh rotation server-side.

### H-03 — CSV fields permit spreadsheet-formula injection

- **Affected:** `backend/src/api/v1/reports/report.service.ts` (`csvCell`, `ordersExportCsv`)
- **Why it matters:** Quoting commas/quotes/newlines does not neutralize fields beginning with `=`, `+`, `-`, or `@`. Customer names, phone values, channel metadata, or order snapshots can become formulas when opened in Excel/Sheets.
- **Likely impact:** A malicious customer-controlled value can trigger external requests, misleading calculations, or platform-specific command behavior on an owner's workstation.
- **Recommended mitigation:** Prefix formula-like cells with a single quote or tab according to the chosen CSV safety policy, including leading whitespace variants. Add tests for all dangerous prefixes and document export escaping.

### H-04 — The required PostgreSQL production datastore and migrations do not exist

- **Affected:** `backend/prisma/`, `backend/src/database/client.ts`, generated Prisma client and deployment configuration
- **Why it matters:** The spec declares PostgreSQL canonical, but the repository contains only a SQLite schema/database and no PostgreSQL migrations or CI path.
- **Likely impact:** The intended production architecture cannot be deployed or validated; SQLite locking/concurrency behavior is unsuitable for multi-user SaaS and masks PostgreSQL-specific query/transaction behavior.
- **Recommended mitigation:** Add a canonical PostgreSQL schema and migrations, environment-specific generation, CI integration tests against PostgreSQL, migration rehearsal, backups/PITR, and transaction/concurrency tests before pilot.

### H-05 — Cancelling fulfilled/completed pre-orders can corrupt reserved inventory and terminal history

- **Affected:** `backend/src/api/v1/orders/order.service.ts` (`preorderTransitions`, `shouldRelease`, `shouldConsumeReservation`)
- **Why it matters:** `READY_TO_FULFILL → FULFILLED` already decrements both `stockQty` and `reservedQty`. A later `FULFILLED → CANCELLED` transition runs reservation release and decrements `reservedQty` a second time. The FSM also permits `COMPLETED → CANCELLED`, although completed orders are terminal in the spec.
- **Likely impact:** Negative/incorrect `reservedQty`, overstated available inventory, and completed sales silently rewritten as cancelled without a defined return/refund flow.
- **Recommended mitigation:** Make `COMPLETED` terminal. Define cancellation versus return semantics after fulfillment; do not release an already-consumed reservation. Add focused tests for cancellation from every pre-order status and inventory invariants before/after fulfillment.

## Medium

### M-01 — Report endpoints aggregate large result sets in Node.js

- **Affected:** `backend/src/api/v1/reports/report.service.ts` (`salesSummary`, `topProducts`, `paymentMethods`, `preorderPipeline`)
- **Why it matters:** The 366-day cap bounds time, not cardinality. Services load every matching order, line item, payment, or open pre-order and reduce them in memory. `topProducts` can load many line items before retaining only the top 10.
- **Likely impact:** Memory/latency spikes and failure to meet the specified p95 under 50k orders, particularly across concurrent tenants.
- **Recommended mitigation:** Move sums/counts/grouping/top-N work into PostgreSQL, add query-specific indexes, and load-test at 10k products/50k orders with concurrent shops.

### M-02 — Several “paginated” lists still scan and materialize all tenant rows

- **Affected:** `backend/src/api/v1/products/product.service.ts` (`list`); `backend/src/api/v1/orders/order.service.ts` (`listWithDerivedPaymentStatus`)
- **Why it matters:** Products are fully fetched, optionally filtered in memory, aggregated, then sliced. PAID/PARTIALLY_PAID order filters fetch all candidate IDs before slicing.
- **Likely impact:** Increasing latency and memory as a shop grows; payment-filtered order pages can become a hot-path bottleneck.
- **Recommended mitigation:** Apply pagination and low-stock/payment predicates in SQL; store or safely derive indexed payment status; aggregate product sales only for page IDs or via a grouped database query.

### M-03 — Sales reports count open/unfulfilled orders as revenue

- **Affected:** `backend/src/api/v1/reports/report.service.ts` (`ACTIVE_ORDER_WHERE`, `salesSummary`, `topProducts`); `backend/tests/integration/reports-milestone-4.test.ts`
- **Why it matters:** The only exclusion is `CANCELLED`; newly created `TO_DELIVER` orders and open pre-orders count immediately as sales revenue. The M4 test explicitly expects an unpaid/open standard order plus pre-order in sales totals.
- **Likely impact:** Dashboard “sales” and top-product revenue can overstate realized/fulfilled sales and fluctuate when orders are later cancelled.
- **Recommended mitigation:** Confirm the accounting definition with the stakeholder. Prefer delivered/completed orders for recognized sales, or label the current metric “orders booked” and provide separate fulfilled revenue/payment-collected metrics. Sync the spec only after the definition is approved.

### M-04 — Authentication endpoints have no abuse controls

- **Affected:** `backend/src/app.ts`, `backend/src/api/v1/auth/auth.routes.ts`
- **Why it matters:** Registration, login, and refresh are public and bcrypt-backed without rate limiting.
- **Likely impact:** Credential stuffing, brute force, registration spam, and CPU exhaustion.
- **Recommended mitigation:** Add proxy-aware IP plus normalized-account throttling, stable `429` errors, backoff, metrics/alerts, and tighter limits for registration/login than refresh.

### M-05 — Order-number generation is race-prone

- **Affected:** `backend/src/api/v1/orders/order.service.ts` (`generateOrderNumber`)
- **Why it matters:** `count + 1` is not a sequence. Concurrent creates can calculate the same number; one transaction then fails the unique constraint instead of creating the order.
- **Likely impact:** Intermittent 409/500-style order creation failures at normal multi-tab or multi-device usage.
- **Recommended mitigation:** Use a per-shop/year atomic counter or PostgreSQL sequence strategy, retry safely on unique conflicts, and add concurrent-create coverage.

### M-06 — Refresh-token rotation can log users out across tabs/devices on concurrent refresh

- **Affected:** `backend/src/api/v1/auth/auth.service.ts` (`refresh` delete-then-issue flow); frontend coordination is only in-memory per tab
- **Why it matters:** Two tabs can refresh the same token simultaneously. One deletes the session; the other fails and clears its local session. There is no reuse-detection family/grace strategy.
- **Likely impact:** Intermittent forced logout and brittle session behavior; replay handling is not observable.
- **Recommended mitigation:** Adopt refresh-token families with a short grace window or atomic rotation semantics, record reuse, and test concurrent tabs.

## Low

### L-01 — Security headers and HTTPS enforcement are not evidenced in the app or deployment config

- **Affected:** `backend/src/app.ts`, repository deployment configuration
- **Why it matters:** No Helmet-equivalent headers, CSP, HSTS, or documented edge policy is present.
- **Likely impact:** Weaker browser hardening if the deployment edge is misconfigured.
- **Recommended mitigation:** Configure headers in Express or the reverse proxy and add deployment checks for HTTPS/HSTS/CSP/frame/referrer policies.

### L-02 — JWT secret validation permits only 16 characters

- **Affected:** `backend/src/config/env.ts`
- **Why it matters:** Operators can provide low-entropy HS256 secrets.
- **Likely impact:** Reduced resistance to offline guessing after token capture.
- **Recommended mitigation:** Require at least 32 random bytes, validate production secrets separately, and document secure generation/rotation.

### L-03 — Integration tests share one fixed SQLite database path

- **Affected:** `backend/tests/helpers/setup-integration.ts`
- **Why it matters:** Separate Jest/agent/CI processes delete and recreate `prisma/sqlite/tests/tmp/test.db`. During this audit, a concurrent verifier run produced “table already exists,” “readonly database,” and missing-table failures.
- **Likely impact:** Flaky parallel CI and unreliable independent verification, even when application behavior is correct.
- **Recommended mitigation:** Allocate a unique temporary database per process/worker, pass its URL before client creation, and clean it after the suite.

### L-04 — Operational observability is minimal

- **Affected:** `backend/src/server.ts`, `backend/src/middleware/error-handler.ts`
- **Why it matters:** Request IDs are returned, but production errors are not logged here and there are no metrics for auth rejection, API latency, report size, export duration, or transaction conflicts.
- **Likely impact:** Slow incident detection and difficult reconciliation of reported order/payment/inventory failures.
- **Recommended mitigation:** Add structured redacted logs, latency/error metrics, audit correlation IDs, and alerts for failed payments, stock conflicts, and slow reports.
