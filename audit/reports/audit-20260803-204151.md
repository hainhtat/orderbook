# Audit Report

Audited scope: COD collection and “COD remaining” cashbook behavior, cashbook APIs, staff daily report, and mobile navigation/layout. Timestamp: 2026-08-03 20:41 (Asia/Yangon).

## Overall risk summary

The implementation is tenant-scoped and input validation is generally present, but COD settlement has a production-impacting correctness defect: the selected wallet is discarded and every collection is posted as Cash. Outstanding COD calculation also excludes partially collected orders, and concurrent collection requests can over-collect an order. These should be fixed before relying on cashbook balances for reconciliation.

## Critical

None found.

## High

### H-01 — COD settlement method is ignored

Affected: `backend/src/api/v1/orders/order.service.ts:831` (and `:828`), `frontend/src/features/orders/order-actions.tsx`.

`collectCod` validates `settlementMethod`, but casts it to `'CASH'` instead of using the requested value. Consequently a rider paid via KBZPay, Wave, or bank is recorded in the Cash account; the COD fee is also posted against Cash. This makes wallet balances and staff reconciliation materially wrong while the UI reports success.

Mitigation: preserve the validated settlement method through payment creation and both cashbook postings; add an integration test asserting each settlement method creates entries in its mapped account and that the fee is debited from that same account.

### H-02 — Partial COD collections are omitted from COD remaining

Affected: `backend/src/api/v1/cashbook/cashbook.service.ts:120-124`.

The account query restricts COD orders to `amountPaidMMK < 1`, so any order with a partial collection (for example, a rider returns part of the amount) is excluded entirely. The displayed COD remaining is therefore understated by the unpaid balance of every partially collected order.

Mitigation: filter COD orders by `amountPaidMMK < totalMMK` (and non-cancelled/eligible fulfillment states), then sum `totalMMK - amountPaidMMK`; add a partial-collection regression test.

### H-03 — Concurrent COD collection can exceed the order balance

Affected: `backend/src/api/v1/orders/order.service.ts:823-837`.

The service reads `amountPaidMMK`, validates the remaining balance, creates a payment, and performs an increment. Two concurrent requests can both pass the stale balance check and together collect more than the order total. Cashbook entries then permanently overstate receipts unless manually reversed.

Mitigation: serialize collection per order (database row lock/serializable transaction where supported) or use a conditional atomic update such as `UPDATE ... WHERE amountPaidMMK + amount <= totalMMK`, checking affected rows before creating payment/entries; add a concurrent-request test.

## Medium

### M-01 — Cashbook account load performs unbounded legacy backfill and N+1 writes

Affected: `backend/src/api/v1/cashbook/cashbook.service.ts:102-113`.

Every accounts request scans all shop payments with no cashbook entry and posts each one sequentially. For a long-lived shop this makes a read endpoint increasingly slow and holds a transaction while issuing one upsert/create per payment, increasing lock contention and timeout risk.

Mitigation: run an idempotent, paginated migration/backfill once (startup/admin job), enforce a unique payment-to-entry constraint, and keep the read path read-only.

### M-02 — Account balances scan all cashbook entries on every request

Affected: `backend/src/api/v1/cashbook/cashbook.service.ts:117-125`.

The accounts endpoint loads every entry for the shop and aggregates in application memory. This grows linearly with transaction history and can become expensive for larger online shops.

Mitigation: add indexed account/date filters and maintain a ledger balance/materialized balance (updated transactionally), or aggregate with SQL/Prisma `groupBy` rather than transferring the full ledger.

### M-03 — Daily report order/product payload is unbounded

Affected: `backend/src/api/v1/cashbook/cashbook.service.ts` daily-report implementation and `frontend/src/features/reports/reports-page.tsx:138`.

The daily report returns all delivered/completed orders and all line items for the day, then renders every order and product row. A high-volume shop can produce a large response and expensive mobile rendering with no pagination or summary cap.

Mitigation: paginate order details, keep totals/aggregates bounded, and add a server-side limit or export path for full detail.

## Low

### L-01 — Mobile shell reserves a large fixed bottom region

Affected: `frontend/src/layouts/app-layout.tsx:6-8`, `frontend/src/components/app-header.tsx:139-140`.

The app reserves roughly nine rem of bottom padding while also rendering a 6rem fixed backdrop and a safe-area-aware nav. This avoids overlap but creates excessive blank space on short pages and is fragile across device safe-area sizes.

Mitigation: derive spacing from the actual nav height plus safe-area inset, or use a shared CSS variable, and verify on iOS/Android viewport sizes.

## Residual risks / follow-up checks

- Add end-to-end coverage for COD settlement wallet mapping, partial collections, duplicate/concurrent submissions, and reversal/reconciliation.
- Confirm production database indexes for `CashbookEntry(shopId, occurredAt)`, `CashbookEntry(paymentId)`, and order payment/status queries.
- Re-run the verifier after H-01 through H-03 are fixed; no specification sync is required unless the approved settlement semantics change.
